# ローカル・クラウド共通の開発手順

このリポジトリは公開用の静的ポータルです。HTML/CSS/JavaScriptをそのまま配信し、ビルドは行いません。外部npmパッケージ、Unity、Python、Docker、Supabaseの認証情報は基本機能の開発に不要です。

## セットアップとテスト

1. このGitHubリポジトリをcloneし、そのルートで作業する。
2. Node.js 24.19.0を用意する（`.nvmrc`）。nvmがある環境では `nvm install` / `nvm use` を使う。Windows等では利用中のNodeバージョン管理ツールで同じバージョンを選ぶ。
3. 次のコマンドを実行する。

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm test
```

`package.json` / `package-lock.json` は開発コマンドとNode要件を管理します。外部依存はないため、サイトのためのパッケージダウンロードは発生しません。

`npm test` は実行用JSの構文、既存の `arcade.test.cjs` / `arcade-layout.test.cjs` / `portal.test.cjs` / `trial-gacha.test.cjs`、開発サーバーのHTTP検査を実行します。失敗時は終了コードが非ゼロになります。PRとmainへのpushでも `.github/workflows/test.yml` が同じコマンドを実行します。

Windowsでシンボリックリンク作成権限がない場合、サーバーのリンク脱出検査だけを理由付きでスキップします。ゲームの検査はスキップしません。

## HTTPで起動する

```sh
npm run dev
```

`http://127.0.0.1:3000/` をブラウザで開きます。終了はCtrl+Cです。作業ディレクトリに依存せず、リポジトリ直下の公開ファイルを配信します。

クラウドのプレビューでは、環境のポート公開機能で3000番を指定し、次のように起動します。

```sh
npm run dev -- --host 0.0.0.0 --port 3000
```

環境が別のポートを要求する場合は `--port` を変更します。Codexのクラウド環境のセットアップコマンドには、リポジトリルートでの `npm ci --ignore-scripts --no-audit --no-fund` を設定できます。環境の設定画面やポート公開方法は利用中の環境に従ってください。

開発サーバーはHTML/CSS/JS・画像・Webフォントだけを配信し、ディレクトリ一覧、隠しファイル、`.env`、`supabase.txt`、Git情報、ルート外へのシンボリックリンクは配信しません。これは開発用サーバーです。公開先は引き続きGitHub Pagesです。

## 公開版と未公開ローカル版の差

- 公開用リポジトリには `common/`、`common.test.cjs`、`supabase/` がありません。これは既存の公開方針です。不足分を空のファイルや仮の認証設定で補いません。
- `index.html` は未配置の共通ファイルを読み込まず、マイページは「準備中」となります。アカウントDOMは将来の統合用に保持しています。
- 無料試験ガチャ、記事コメント、ゲストブック、ミニゲーム記録はブラウザのlocalStorageを使い、Supabaseへは接続しません。プレビューのURL・ブラウザが変わると保存先も変わります。
- 従来のPC作業フォルダにある `.publish-aniani/` は別のGit作業ツリーです。cloneしたリポジトリ内に作る必要はありません。PC側から同期する場合は最新のmainとの差と秘密情報の混入を確認してください。

## Supabaseを開発するために残っている作業

2026-10-09のクラウド調査では、ネットワーク制限が適用中で、次の2ホストは許可されていません。通常のプロキシ経由のHEADリクエストは認証前に403で拒否されました。

- `esm.sh`（未公開ローカル版のSupabase SDK配信）
- `bjrewemniqfchggrrkdd.supabase.co`（既存Supabaseプロジェクト）

共通機能の開発を行う場合は次を確認する必要があります。

1. 所有者が保持する元の `common/`、`common.test.cjs`、`supabase/` を確認し、統合する範囲を決める。
2. クラウド環境の正式なネットワーク設定で上記ホストを許可する。設定変更は環境のレビュー手順に従う。プロキシやTLS検証は無効にしない。
3. 元実装が必要とする公開クライアント設定を確認し、所有者が既存の接続情報を安全な設定経路から用意する。キー・トークンはこの文書やGitへ追加しない。
4. ローカルHTTP URLとクラウドプレビューURLがSupabase Authのリダイレクト許可リストに含まれるか確認する。現在の許可リストは未検証。
5. テスト用プレイヤーによる認証E2Eと、元の検証SQLを使ったロールバック前提の検証を行う。適用済みmigrationは再実行しない。

今回の403からキーの有効性は判断できません。認証情報の作成、DB変更、メール確認の無効化は行っていません。現時点では共通アカウント・DB開発の準備完了とは扱いません。

## クラウドのブラウザと外部フォント

Google Fontsの `fonts.googleapis.com` / `fonts.gstatic.com` は許可されています。2026-10-09の確認ではPythonのTLS検証付きリクエストは成功しましたが、クラウドのChromiumでは `ERR_CERT_AUTHORITY_INVALID` が発生しました。環境のCAファイルとNSSへのCA登録は確認済みです。Chromium側の信頼ストア・プロキシ証明書の扱いを含め、環境のセットアップ手順を確認する必要があります。証明書検証を無効にして回避しないでください。

ゲームや無料試験ガチャのテストは外部フォント・Supabaseを必要としません。クラウドのブラウザ確認ではフォント読み込み結果も分けて記録してください。

## Gitでの作業

cloneしたリポジトリで作業ブランチを作り、`npm test` とPC・モバイル幅の確認後にコミットし、main向けPRを作ります。公開を依頼されるまでmainへマージしません。認証情報を含む `.env` / `supabase.txt` はGit対象外です。
